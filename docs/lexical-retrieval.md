# 纯词法检索：设计与实测

本文汇总 2026-10-25 至 2026-10-29 这一轮对检索链路的改动。目标是在不引入向量模型的前提下，让 2C/2G 服务器也能稳定支撑知识库查询。

## 1. 为什么不使用向量

- 本地 `qwen3-embedding:0.6b` 建索引约 0.8 chunk/s，1000 章需要按小时计
- 查询侧虽然只要 30 ms，但模型常驻约 1 GB 内存，服务器只有 1.9 GB 且 swap 已用 845 MB
- 实测 dense 只对少数换述查询有增益，而卡片摘要修复、实体词典、同义词扩展的收益更直接

因此默认关闭 dense，保留 `embedding_indexing_enabled=False`。

## 2. 检索链路

```
导入 → 解析（实体/事实/身份）
     → 发布（自动重建该来源的 chunk FTS + 卡片 FTS）
     → 查询：
         实体名注册（jieba 词典）
         → 精确短语优先，OR 兜底
         → 同义词扩展（数值/功法/提升/等级）
         → 知识卡片 + 原文段 + 证据引用
     → 实体 dossier（按身份组直接读结构化投影）
```

### 2.1 实体词典

jieba `HMM=False` 会把「杨凌」「韩萧」切成单字。`search_planned` 首次进入某个 work 时，从知识库读取实体名/别名并 `jieba.add_word` 注册；索引侧用同一词典。

- 索引保存注册名的**多字组件**（「风神金刚腿」→「风神」「金刚」），部分名查询仍可召回
- 旧索引没有注册名 token 时，无显式短语约束的查询退回字符 OR，避免静默返回 0 条
- 显式短语过滤（`required_phrases`）保持严格，不退回字符匹配

### 2.2 短语优先

`search_lexical` 先跑精确短语查询，再用 OR 查询补足，短语命中排前。

### 2.3 同义词扩展

| 原词 | 扩展 |
|---|---|
| 数值 | 属性、力量、敏捷、精神、点 |
| 身体 | 属性、力量、敏捷 |
| 提升 | 增幅、增加、提高、加成、飙升 |
| 功法 | 内功、武技、技能、秘籍 |
| 属性 | 数值、力量、敏捷、精神 |
| 增幅 | 提升、增加、加成 |
| 等级 | 级、境界、修为 |

chunk 搜索和卡片搜索都生效。

### 2.4 卡片

已发布候选 100% 投影为卡片（10 章库 735/735）。实体卡无别名时摘要退回实体名，不再退化成分类名（`ability`/`character`）。

### 2.5 实体 dossier

`query_entity_dossier(space, work_id, entity, branch)`：实体名 → 身份组 → 直接读 facts/relations/events，不经过全文检索。10 章库杨凌 209 条、韩萧 68 条。

## 6. 已知限制

- **别名**：抽取模型自由填 `identity_aliases` 会产生错误别名（并列势力互指），已回退；「杨老大」这类称呼召回仍弱
- **换述召回**：同义词表覆盖有限，复杂换述仍可能漏召回
- **时间线**：独立项目没有持久化 writing manifest，数字型 `narrative_position` 现在 fail-closed；需要时用 `reader_position`
- **排序浮动**：卡片和原文段的首位会随覆盖模式浮动，但同一张卡片通常同时附着在原文段上

## 7. 与向量方案对比

| 维度 | 纯词法 | 本地向量 |
|---|---|---|
| 服务器内存 | 181 MB | +1 GB 以上 |
| 建索引 | 5 秒/全库 | 0.8 chunk/s |
| 热查询 | 0.13–0.44s | 0.13–0.84s（dense 额外 45–88ms） |
| 换述召回 | 依赖同义词/卡片 | 更好 |
| 运维复杂度 | 低 | 高（模型、索引、维度） |

结论：当前规模与服务器条件下，纯词法是更合适的选择；需要更强换述时再考虑远程 embedding API，而不是本地模型。
