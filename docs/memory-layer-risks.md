# 记忆层与现有系统的风险分析

> 目的：在动手实现前，把“解析、使用、效率、质量、冲突、现有问题、优化、新问题”逐项摊开。
> 结论：现有系统能跑，但有 5 个 P0 级正确性问题；记忆层方案本身可行，但会引入 7 类新风险，需要先立规矩再写代码。

## 1. 现有系统的 P0 问题

### P0-1 章节号会全部塌成 1

**证据**：`kb_source_meta` 为 0；`next_chapter_index()` 连续调用返回 `1, 1`。

```python
# scripts/kb_server.py::_run_archive_update
chapter_index = int(chapter) if chapter is not None else archive.next_chapter_index(...)
```

- 现有 10 章没有 meta
- 循环里不写 meta
- 每章都拿到 1

**影响**：对存量作品跑 `state_update`，10 章快照全部落在第 1 章，回滚和 `at_chapter` 全错。

**方案**：
1. 从来源标题解析章节号（`0313 第313章` → 313）
2. 解析失败则按 `created_at` 顺序编号
3. 写入 `kb_source_meta` 后再取下一号
4. 提供一次性回填脚本

**新问题**：标题不规范时编号仍可能错；需要人工校正入口。

### P0-2 两套事实源会分叉

解析链路写 `knowledge_item`，档案链路写 `kb_entity_snapshot` / `kb_story_record`，两边都声称是“事实”。

**影响**：同一属性两个值，编译与检索各说各话。

**方案**：明确权威层级

```text
source（原文）
  > scene/assertion（记忆层，canon）
  > entity snapshot（当前状态投影）
  > archive_entry（派生视图，可重建）
  > knowledge_item（检索投影）
```

档案条目必须挂 `source_assertion_ids`，可回查。

**新问题**：回填旧数据时无法一一对应；需要“未溯源”标记。

### P0-3 没有章节记忆，三份提示词无处落地

现状只有原子事实，缺 scene / assertion / thread。`提取细纲` 的场景因果、认知标签、未决线程都无法存。

**方案**：按设计稿加 L1/L2/L3 三层（见 `memory-layer-design.md`）。

**新问题**：与现有 parse 抽取重复，需要明确“谁写哪一层”。

### P0-4 as-of 泄漏

**证据**：`archive.related_entities()` 调 `get_snapshot()` 不传 `at_chapter`，永远取最新。

**影响**：查询第 1 章实体，会带出第 10 章才建立的关系。

**方案**：
1. `related_entities(..., at_chapter)` 全链路透传
2. `search` 增加 `at_chapter`
3. 校验器：所有读取路径必须显式带 as-of

**新问题**：API 参数变多；默认“最新”仍可能被误用。

### P0-5 解析任务会互相踩

**证据**：重跑失败批次时出现 `KnowledgeItemVersionConflictError: event reconciliation receipt generation changed`。

**原因**：同一作品可同时起多个 parse job；线程各自建批次、发布、写 receipt。

**方案**：
1. 每作品一把任务锁（DB 行锁或进程锁）
2. 同一作品任务串行，跨作品并行
3. 批次幂等键 `(work, source_ids, prompt_version)`
4. 失败重试只重跑失败阶段

**新问题**：串行会拉长总时长；需要优先级队列。

## 2. 现有系统的 P1 问题

| 编号 | 问题 | 证据 | 影响 | 方案 | 新问题 |
|---|---|---|---|---|---|
| P1-1 | 实体词典缓存不失效 | `_registered_entity_terms` 只写不删 | 新实体发布后，查询仍按旧分词，召回不到 | 按 `work + entity_version` 缓存，发布时递增 | 版本号要持久化 |
| P1-2 | 首章账本从 0 开始 | 实测首章 `ledger={"铜钱":-400}` | 余额为负 | 抽取首章时读“初始余额”字段；无则记 `unknown` | 模型可能编初始值 |
| P1-3 | 死人过滤只认精确查询 | `search` 只在 `q == 死亡名` 时拦截 | 背景提及仍会召回 | 词法池过滤 + `include_inactive` 分级 | 误杀正常回忆 |
| P1-4 | 编译模块四不完整 | 只按 outline 匹配 + 主角 1 度 | 漏掉本章实际出场者 | 用 scene.participants 补全 | 场景未抽取时退化 |
| P1-5 | LLM 审校不可复现 | 温度 0 仍会波动 | 同一稿两次结论不同 | 记录 prompt/model/输入 hash；证据引用 | 存储与回放成本 |
| P1-6 | 档案抽取无场景校验 | 直接 LLM→snapshot | 可能凭空补状态 | 先章节记忆，再档案；交叉校验 | 多一次调用 |
| P1-7 | `story_record` 只追加 | 无 entry_key/revision | 长期档案重复叠加 | 迁移到 `archive_entry` | 迁移期双写 |
| P1-8 | 派生数据无 provenance | snapshot/story_record 无 run_id | 无法追责 | 全表加 `run_id`、`evidence` | 表变大 |
| P1-9 | 档案表无 schema 版本 | `ensure_schema` 只建表 | 加字段时旧库不升级 | `schema_version` + 迁移 | 迁移失败回滚 |

## 3. 现有系统的 P2 问题

| 问题 | 证据 | 方案 |
|---|---|---|
| 搜索慢 | 冷 3 s，热 0.8–1.1 s | 预热 + 缓存 + 索引 + 两阶段召回 |

| 无备份策略 | 手工 | 每日 `.backup` + 保留 7 天 |
| 无负载测试 | 未做过 | 50 并发读 / 5 并发写 |

## 4. 记忆层带来的新问题

### 4.1 scene

| 新问题 | 说明 | 缓解 |
|---|---|---|
| 存储膨胀 | 每章 5–15 段散文 | 只存摘要 + 证据引用；原文不复制 |
| 与 event 重复 | 同一事两处 | scene 为叙事权威，event 为检索投影 |
| 切分不稳 | 模型切太碎/太粗 | 最小因果链长度 + 序号连续校验 |
| 证据伪造 | quote 不在原文 | 子串定位，失败拒绝 |

### 4.2 assertion

| 新问题 | 说明 | 缓解 |
|---|---|---|
| 组合爆炸 | 每个角色 × 每个信念 | 只记录“有剧情作用”的断言 |
| 矛盾断言 | 两个 holder 相信相反 | 允许并存，按 holder 查询 |
| holder 歧义 | 叙述者 vs 角色 | 强制字段 + 枚举 |
| 认知更新链 | 旧判断被替代 | `supersedes_id`，不删除旧记录 |

### 4.3 thread

| 新问题 | 说明 | 缓解 |
|---|---|---|
| 重名/改名 | `[矿工比试]` vs `[矿工大赛]` | 注册表 + 别名 + 候选评审 |
| 合并/拆分 | 两条线其实一条 | 合并保留历史，不物理删 |
| 僵尸线程 | 长期无进展 | `blocked` + 超期归档 |
| 线程爆炸 | 每章都建新线 | 准入规则：必须跨章影响 |

### 4.4 line_network

| 新问题 | 说明 | 缓解 |
|---|---|---|
| 版本爆炸 | 每批 × 2 轮 | 只保留 accepted + 最近 2 版 |
| 评审负担 | 每批都要看 diff | 自动校验 + 抽样人工 |
| 边界漂移 | 模型顺移范围 | 范围写死 + 校验 |
| 章节号隐藏 | 内部要定位 | `chapter_anchors` 分离 |
| 跨批不一致 | 新批推翻旧批 | 上版为基线 + 变化必须解释 |

### 4.5 archive

| 新问题 | 说明 | 缓解 |
|---|---|---|
| 上下文装不下 | 档案无字数上限 | 模块索引 + 受影响条目切片 |
| 跨栏重复 | 同规则写两处 | `entry_key` + 模块归属 |
| 动态叠加 | “原为 X 现为 Y” | 校验器拒绝 |
| 版本存储大 | 每章全量文档 | 只存 diff + 定期快照 |
| 流转误判 | 角色还没退场 | DB 规则 + 人工确认 |
| 与 story_record 双写 | 两套记录 | 迁移期只写 archive_entry |

### 4.6 as-of 与检索

| 新问题 | 说明 | 缓解 |
|---|---|---|
| 索引变多 | 每表都要 as_of | 复合索引 `(work, as_of, ...)` |
| 默认值歧义 | 最新 vs 指定章 | API 显式 `at_chapter`，默认最新并标注 |
| FTS 中文分词 | 长散文切词差 | 实体词典 + 短语优先 + 摘要 |
| 排序困难 | 结构信号多 | 先规则排序，再模型重排（可选） |

### 4.7 评审与治理

| 新问题 | 说明 | 缓解 |
|---|---|---|
| 人工瓶颈 | 每章都要审 | 自动接受低风险，抽样高风险 |
| 拒绝理由丢失 | 无法复盘 | `review` 表存理由 |
| 权限 | 谁能接受 canon | 角色权限 + 审计日志 |

## 5. 效率：优化清单与预期

| 优化 | 现状 | 预期 | 风险 |
|---|---|---|---|
| 启动预热 jieba + 实体词典 | 首查 +0.6–1.4 s | 首查接近热查 | 启动慢 1 s |
| 实体词典版本缓存 | 发布后失效 | 新实体即时可查 | 版本管理 |
| SQLite 调优 | 默认 | `cache_size=-20000`、`mmap_size=256MB`、`temp_store=MEMORY`、`ANALYZE` | 内存占用 +20 MB |
| 两阶段召回 | 全量 join | 先 FTS top 50，再 join/rerank | 可能漏召回 |
| 结果缓存 | 无 | 热查询 <50 ms | 数据更新后要失效 |
| 编译缓存 | 每次重算 | 同版本秒回 | 缓存键要含 archive 版本 |
| 解析批处理 | 单章串行 | 批内并发 2（内存允许时） | 2C/2G 易 OOM |
| 模型路由 | 全部 DeepSeek | 抽取用小模型，审校用大模型 | 质量波动 |

目标：热查询 P95 < 300 ms；冷启动首查 < 1 s；单章解析 < 40 s。

## 7. 冲突矩阵

| 冲突 | 现状 | 裁决 |
|---|---|---|
| 原子事实 vs 场景 | 两套 | scene/assertion 为叙事权威，knowledge_item 为检索投影 |
| parse 抽取 vs 章节记忆 | 都会写状态 | 章节记忆写 snapshot，parse 只写事实投影 |
| archive vs story_record | 两套记录 | archive_entry 权威，story_record 仅原始日志 |
| 编译事实 vs 写作指令 | 混在一起 | 分区：`facts` / `directives` |
| 最新 vs as-of | 默认最新 | 显式 `at_chapter`，默认最新但返回标注 |
| 拆书库 vs 连载库 | 同库不同 work_type | 数据隔离，禁止跨库引用 |
| 模块归属 vs 分类 | 多模块可写同一事实 | 模块归属表 + entry_key 唯一 |
| 章节号 vs 无章节号 | 线网禁止章节号 | 内部锚点，渲染剥离 |

## 9. 结论

- 现有系统的主要问题不是“模型不行”，而是**章节号、as-of、双事实源、任务并发、缓存失效**这五个工程问题。
- 记忆层的方案可行，但必须先解决这五个 P0，否则场景/线程/档案都会建在错误的地基上。
- 最大的新风险是**版本与评审负担**：线网和档案都会产生大量版本，必须用 diff + 自动校验 + 抽样人工控制。
- 效率上，先做预热、缓存、索引，目标热查询 < 300 ms；不要一上来加向量库。
- 质量上，先立“证据、as-of、单一事实源”三条硬规则，再谈模型效果。
